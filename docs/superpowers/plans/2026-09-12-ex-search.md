# ex-search Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a dependency-free-at-runtime Manifest V3 extension that augments traQ message search with configurable history, local suggestions and completion, friendly filters, highlighting, and visible-page relevance ordering.

**Architecture:** Load UMD-style global modules in content-script order so the unpacked extension needs no bundler: `core.js` owns pure data logic, `dom.js` owns bounded DOM transformations, `app.js` coordinates storage and SPA lifecycle, and `content.js` starts the app. Test the pure and DOM layers in Node with jsdom; test Chrome storage through fakes.

**Tech Stack:** Manifest V3, browser JavaScript, Chrome storage API, CSS, Node.js 18 `node:test`, `node:assert/strict`, and development-only `jsdom@26.1.0`.

## Global Constraints

- Run only on `https://q.trap.jp/*` and request only the `storage` permission.
- Do not call `/api/v3`, read authentication data, inject into the page's JavaScript world, or depend on Vue/Pinia internals.
- Do not modify traQ or traQ_S-UI.
- Keep runtime files build-free and free of third-party imports.
- Locate search primarily with `input[placeholder="メッセージを検索"]`; never hard-code a complete generated CSS hash.
- Keep settings in `chrome.storage.sync` and versioned extension history in `chrome.storage.local`.
- Store query history only; never persist visible message text or extracted frequent terms.
- History limit is 1–100 with default 20; suggestion result limit is eight.
- Local relevance reorders only the currently rendered result page and must be labeled accordingly.
- Use test-first red-green-refactor cycles for every new behavior.

## File map

- `manifest.json`: Manifest V3 metadata and ordered content-script entries.
- `package.json`, `package-lock.json`: test commands and jsdom development dependency.
- `core.js`: UMD/global pure settings, history, query, token, ranking, and completion functions.
- `core.test.js`: pure behavior tests.
- `dom.js`: UMD/global search discovery, input updates, highlighting, scoring, and ordering.
- `dom.test.js`: jsdom fixture tests.
- `app.js`: UMD/global storage adapter, panel rendering, listeners, observer lifecycle, and reconciliation.
- `app.test.js`: jsdom plus fake-Chrome integration tests.
- `content.js`: minimal startup adapter.
- `content.css`: styles scoped to extension-owned data attributes and highlight marks.
- `options.html`, `options.css`, `options.js`: settings and history clearing UI.
- `manifest.test.js`: permissions and entry-point contract.
- `README.md`: installation, use, privacy, limitations, and tests.

- [ ] **Step 1: Write failing query-filter tests**

Assert exact family replacement and preservation:

```js
assert.equal(
  applyOwnedFilters('hello in:#general from:alice has:image custom:value', {
    scope: 'in:here', author: 'not:bot', target: '', content: 'has:audio', after: '2026-09-01', before: ''
  }),
  'hello custom:value in:here not:bot has:audio after:2026-09-01'

```

The owned families are `in:`/leading `#`, `from:`/`by:`/`is:bot`/`not:bot`,
`to:`/leading `@`, `has:attachments|image|video|audio`, `after:`/`since:`, and
`before:`/`until:`. Preserve unknown colon terms and quoted free text.

- [ ] **Step 2: Verify filter tests fail for missing exports**

- [ ] **Step 3: Implement a quote-aware splitter and family replacement**

`splitQuery(query)` returns tokens while preserving quoted phrases such as
`"release notes"`. `applyOwnedFilters(query, values)` removes only owned
families, appends non-empty validated replacements in the fixed order scope,
author, target, content, after, before, and joins tokens with one space.

- [ ] **Step 4: Write failing term extraction tests**

- [ ] **Step 5: Implement term extraction and visible-text frequency**

`extractFrequentTerms(texts, limit = 8, segmenter = defaultSegmenter)` returns

- [ ] **Step 6: Write failing context, ranking, and completion tests**

- [ ] **Step 7: Implement deterministic ranking and completion**

- [ ] **Step 5: Implement debounced reconciliation**
